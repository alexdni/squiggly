## ADDED Requirements

### Requirement: TypeScript Feature Extraction
The system SHALL compute EO/EC features in server-side TypeScript with the result schema previously produced by the Python worker: `band_power`, `alpha_peak`, `band_ratios`, `asymmetry`, `connectivity` (wPLI matrices and network metrics), `lzc`, `risk_patterns`, `qc_report`, `rejected_epochs` and `processing_metadata`, plus `spectrograms` data.

#### Scenario: Band power
- **GIVEN** kept 2 s epochs for a condition
- **WHEN** features are computed
- **THEN** each channel has absolute (µV², Welch 1 s segments, trapezoid integration) and relative power for delta, theta, alpha1, alpha2, smr, beta2, hibeta and lowgamma

#### Scenario: Numerical parity with Python reference
- **GIVEN** committed fixtures generated by the former Python worker from the same synthetic epochs
- **WHEN** the TS feature functions run on them
- **THEN** band powers match within 2 % relative error, peak alpha within 0.2 Hz, wPLI within 0.05, and normalized LZC within 0.02

#### Scenario: Engine recorded
- **WHEN** results are saved
- **THEN** `processing_metadata.engine` identifies the Node pipeline and the biofeedback-core version

### Requirement: TheraQ Metrics On Server
The system SHALL compute TheraQ phase-comparison metrics (amplitude spectra, `theraq_definitions.json` evaluation, 0–10 scores with traffic-light ratings, adaptive MAD epoch rejection) on the server in TypeScript and persist them to `project_analyses`.

#### Scenario: TheraQ run
- **GIVEN** a project with EO1, EC, EO2 and TASK recordings containing O1, Cz, F3 and F4
- **WHEN** the user runs TheraQ analysis
- **THEN** the four files are processed server-side, and the resulting `metrics` and `indices` are saved and rendered in the TheraQ report

#### Scenario: TheraQ parity
- **WHEN** the ported metric engine runs the cases from the former `test_theraq_metrics.py`
- **THEN** it produces the same scores and ratings
